RP Hub 魔改版：修改时必须保留的当前实现
更新时间：2026-10-13

一、部署与文件边界

1. 根目录 `_worker.js`、`magic-extension.js`、`DB/bootstrap.js`、`DB/dirty-tracker.js` 是正本。
   `page/` 中同路径文件是部署副本，发布前必须逐字节一致；`page.zip` 只包含这四个文件。
   面板/锁页样式不再有独立 styles.css 文件：由 bootstrap.js 启动时自注入 `<style>`（`SYNC_STYLE_TEXT` 与 `LOCK_STYLE_TEXT`）。

2. Worker 保持单文件、无构建步骤。不要加入 import、顶层 await 或运行时依赖。

3. R2 binding 固定为 `RP_SYNC_R2`；可选密码固定为 `RP_SYNC_PASSWORD`。
   外部适配地址固定在 `_worker.js` 的 `DEFAULT_ADAPTER_URL`。
   `RPHUB_ADAPTER_URL` 只允许本地 `file://` 测试覆盖。
   部署器（deployer/worker.js）新增的 `/api/projects`、`/api/project-check`、`/api/update` 依赖同一对常量做"魔改版项目"判定（生产配置同时含该密码变量与该 R2 绑定）；判定只看键名存在性，不得读取或回传变量值。`/api/update` 服务端必须保留二次校验，防止绕过前端刷新非魔改版项目；更新不改密码、不动 R2 数据。

4. 未注册路径继续回源作者站。作者 app.js、其他作者脚本、HTML 动态加载器和更新检查 meta 保留原文，不做源码替换。
   当前作者适配唯一维护入口为 adapter/rp-hub.js：头部 RPHUB_ADAPTER_CONFIG 注释是 schema 2 元数据，下方是可执行外部脚本。适配层不再包含作者源码改写或来源校验入口。

5. 主页成功时按顺序注入 dirty-tracker、页面固定元数据、外部适配脚本正文、magic-extension、bootstrap。
   脚本随 HTML 内联执行，并非再次用浏览器 src 拉取；后续 app.js 请求始终原样代理，不因适配源恢复而改变。
   脚本读取/元数据校验失败且 last-good 也不可用时，主页只注入 dirty-tracker。其他作者 HTML 同样只注入 dirty-tracker。
   不保留客户端 6 秒拉取/补装循环；源恢复后刷新页面启用增强。作者 HTML/JS GET、HEAD 使用 no-store，本地资产仍按第 7 条。

6. 外部适配和作者页面直连 GitHub。适配 URL 固定为 main/adapter/rp-hub.js；失败后校验 R2 rp-adapter/last-good-script-v1.js，成功缓存 30 秒、失败缓存 5 秒。
   Worker 不执行外部 JavaScript，只读取头部元数据 JSON 并检查契约标记；last-good 不是任意脚本语法/运行正确的证明，发布前必须检查与回归。
   功能模块通过 window.RPHubExternal(version:1) 使用 flush、context、describeCard、register、imageKey、capabilities、installUi。bootstrap manualSave 直接调用该版本化 flush。
   flush 主动运行保存防抖任务并等待存储 Promise/事务完成。未就绪、生成/切换中或写入失败须拒绝，不得靠固定延迟猜测成功。
   当前适配依赖 Vue3 setup/watch/onMounted、RPHubStorage/RPHubComposables 和四类保存 watcher 函数文本标记；作者改变这些接口时仍需修改适配脚本。
   图片接入在作者卡片观察回调之前进行，没有全局 fetch/XHR 包装。缺少角色/分支/消息上下文时不接管作者任务。
   UI 条件渲染需保留判空、reconcile 每步独立兜底、根节点 subtree 观察；YNAI 模型数据缓存与 select 实例分离，新元素必须重绘。

7. 三个注入静态文件（dirty-tracker、magic-extension、bootstrap）的资产缓存固定为 no-cache 协商缓存：每次部署 etag 必然变化，刷新必然拿到当前部署副本（409 版本门语义），未变化请求 304，不重复下载未变资产；不得退回 no-store。

8. 开屏访问门禁：主页与恢复页由 bootstrap.js 在站点打开时先静默做一次同步密码校验（`auth-status` 单次请求，`retryCount: 0`、8 秒超时）。**已保存密码（`rp_hub_sync_password_v1`）验证通过时全程不出现任何登录 UI**，照常进入站点；只有云端要求密码且本地没有有效密码时（未保存过，或已失效被清空）才显示登录锁页（z-index 10000，面板与锁页样式均由 bootstrap 自注入，不依赖外部样式表加载时序；body 为 null 时挂到 documentElement；浅色纯 CSS 极光背景 + 玻璃卡片，徽标 + 眼睛明文切换 + 抖动错误 + spinner + `prefers-reduced-motion` 降级）。锁页表单提交正确密码后保存到该 key，同步弹窗与图片管理页照常复用（图片管理页本就自动用该 key 登录），正常使用中不再弹出密码框（原 401 兜底密码弹窗保留，用于会话中途改密）。云端不可达直接放行（首屏静默路径网络失败即放行；锁页表单态的提交失败显示错误并可重试，刷新页面同样回到静默放行路径）：门禁只是体验层，真正的数据防护始终由 Worker 端 401 承担，不得因网络故障把整站锁死。恢复页在门禁放行（静默或表单解锁）后才开始拉取；测试与代码不得依赖 body children 顺序定位同步面板。

9. bootstrap.js 与 dirty-tracker.js 的协议常量（journal/intent/epoch/restore 标记、RESTORE_PAGE 判定）是人肉双写副本，两侧均有互指注释；audit-regressions.mjs 的静态断言逐字比较两侧声明，任何一侧改名必须双侧同步。同步请求不再使用跨标签页 Web Locks 排队；当前页面的 `operationPending/syncing` 只负责防重复点击。恢复期间的跨标签页写保护由 RESTORE_ACTIVE_KEY storage 信号（其他标签页暂停写入并显示遮罩）+ 恢复标签页自身的 IndexedDB write barrier（等待在途写事务收尾）承担。

二、同步协议硬约束

1. 当前协议：
   - snapshot：`rp-sync-paged-jsonl-v4`
   - schema：13
   - root：`rp-sync-manifest-root-v1`
   - page：`rp-sync-manifest-page-v1`
   - upload session：`rp-sync-upload-session-v1`

2. 当前 R2 布局：
   - `rp-sync/main/manifest.json`
   - `rp-sync/main/manifests/<root-checksum>/<page>.json`
   - `rp-sync/main/packs/<sha256>.bin`
   - `rp-sync/main/blooms/<sha256>.bin`
   - `rp-sync/main/uploads/<root-checksum>.json`
   - `rp-sync/main/maintenance/gc-v1.json`（GC 游标与删除前复核状态）
   - `rp-sync/main/migration-v13.done`

3. 初始化是非破坏式的。缺少 v13 标记时只写初始化标记并记录旧 manifest etag；不得批量删除 `rp-sync/main/`，不得触碰 `rp-images/`。

4. 单次 HTTP 请求只上传一个 pack，客户端在途并发固定为 4（重叠网络往返；每个请求仍是独立、幂等的 put，失败互不影响，断点续传语义不变）。每个 pack 最大 1MiB、512 条；Worker 必须把 `request.body` 直接传给 R2 `put`，并传入 32 字节 SHA-256 digest。
   不得在 Worker 中读取、拼接、逐字节扫描或重新 hash 1MiB pack 正文。

5. 上传顺序固定：
   `prepare-upload` → 可选 `initialize-storage` → `begin-upload` → `upload-bloom` →
   `upload-manifest-page` → 缺失时逐包 `upload-pack` → 重交页面 → `finalize-upload` → 串行 `gc-step`。

6. 同一个 snapshot checksum 的上传重试要返回现有进度；会话按 checksum 复用已上传的页和 pack，不因当前云端根版本或 GC 状态变化而重置个人存档。丢失 finalize 响应后必须先核对当前根，确认已提交则直接返回，不重复提交。

7. 每个 manifest page 最多 32 个 pack，按 page index 顺序提交。页 hash 必须绑定页号、前页 hash 和 pack 元数据；最后页 hash 必须等于 root 的 `pageRoot`。
   页链、Bloom、总量校验后先以 `etagDoesNotMatch: '*'` 保存不可变声明；有缺包时不推进会话，全包验证成功后用 etag CAS 推进。
   upload-pack 必须核对当前页或紧邻上一页的 checksum/length/entryCount；同元数据幂等 204，已有元数据不同则 409，不能覆盖。新对象条件创建，正文继续直接传 R2。

8. 页面验证每页最多并发 6 个 R2 `head`，且同时核对 pack size 与 `customMetadata.entryCount`。同 checksum 的重复项必须 length 和 entryCount 都一致。
   upload-pack 校验成功的包按 checksum 在 isolate 内记入验证缓存（对象不可变、活动会话期间受 GC 保护）；upload-manifest-page 的页提交复核只 head 缓存外的包，缓存值与页声明不一致仍按元数据冲突处理。

9. Bloom 固定 32KiB。上传时由 R2 校验 SHA-256；manifest page 验证其包含关系；finalize 写根前重新读取并校验 Bloom。
   Bloom 假阳性只允许多留垃圾，绝不能产生假阴性删除当前数据。

10. 根 manifest 必须保持常数大小，不包含完整 pack 数组。根切换保留 ETag 条件写作为完整性保护；begin/finalize 不使用全局 mutation lock，也不因普通根版本变化向用户返回 409。finalize 在 CAS 失败时重新读取当前根并继续提交当前完整 snapshot（最多 3 轮，无竞争首轮必成功），最后成功完成的快照成为云端存档。GC 删除前必须重新读取当前根和 Bloom，并保护所有可完整枚举、仍可能 finalize 的上传会话；无法完成复核时跳过本轮删除。写入结果未知时先核对根、会话和对象状态，不能证明成功或安全时才返回未知结果，不建立永久阻塞锁。
   manifest 状态读取在 isolate 内按 key/etag 缓存；legacy etag 迁移复核观察到 etag 已变化后用 WeakSet 永久短路，不再逐请求重 head 旧根。清单页在 isolate 内按 (根校验码, 页码) 共享缓存（上传侧与拉取侧同一批不可变页对象）。

11. 下载 pack 必须绑定已提交清单位置：version、pageIndex、packIndex、checksum、length、entryCount 全部匹配后才读取 R2。不得只信任客户端提交的 checksum。

12. 下载清单页与 pack 的客户端在途并发固定为 4。内部恢复文档是安全执行边界：必须卸载作者应用、不触发任何业务写入，并立即把地址栏还原为 `/`；用户界面只显示统一恢复进度，不暴露内部路由或下载/校验/应用/索引阶段。

13. 恢复必须保持两遍安全语义：
   - 下载批次直接复用内存字节完成长度、SHA-256、JSONL 数量、对象顺序和 bucket/group 归属的完整预校验，再写 staging；预校验失败不得触碰业务数据；
   - 全部预校验成功后才设置恢复标记（其他标签页收到信号后暂停写入并显示遮罩，恢复标签页用写屏障等在途写事务收尾）；第二遍每批最多 4 pack 从 staging 读取一次，同时恢复业务数据、重建 entry 缓存并批量缓存原始 pack。普通记录写入同时受 64 条和约 8MiB 估算字节上限约束。缓存 canonical bytes 用 new Uint8Array(canonicalBytes) 精确复制，禁止持久化整个 pack 的共享 backing buffer。
   不得退回三遍 JSON 解析、每 pack 一个 staging/cache 事务，也不得取消 staging 后重复下载 300MB 快照。进入覆盖阶段后失败必须保留暂停标记，完整重试成功后才能清除。缓存只识别当前 256 桶/32 项数组布局：旧 32 桶/128 项快照在放置校验处报错（不静默转换、无自动索引迁移）；恢复时命中本地缓存的 pack 只验证长度（写入缓存前已按 checksum 完整验证过），长度不符回退服务器下载，下载路径仍做完整 SHA-256 校验。

14. GC 只能由显式 `gc-step` 请求执行，不放进 finalize、`waitUntil` 或长连接。GC 状态 `rp-sync-gc-state-v2` 按 `packs → manifest-pages → blooms → uploads` 四阶段持久化独立游标；根 checksum 变化时整体重置、从新根完整扫描（旧 gc-v1 状态只保留 pack 游标）。每步最多 list 256 个对象（uploads 阶段 16 个会话）；只删除当前根与活动会话都明确不引用、且超过对应宽限期（pack/控制对象 24 小时）的对象；游标用 ETag CAS 持久化，CAS 竞争静默放弃本次推进；游标持久化并可在边界对象被删除后继续。

15. GC 保留依据只有当前根与活动 upload session：pack 用当前根 Bloom + 活动会话 Bloom 并集保护；旧 manifest page / 旧 Bloom 按内容寻址归属（不属于当前根 checksum、不属于活动会话 checksum 集合）回收；upload session 超过 7 天 TTL（createdAt/updatedAt/R2 时间最大值）自动清理，删除前逐个重读复核，过期会话删除后 begin-upload 可为同一 checksum 建立新会话。活动会话枚举或对象校验失败时保护不完整，该轮只推进游标不删除。

三、严格增量不变量

1. 第一次上传可完整扫描。正常增量上传不得对 `RPHubDB/store` 或 `AICharGen/characters` 打开全量 readonly cursor；只读取日志候选键。

2. 业务 IndexedDB 写入和 `__rp_sync_journal_v2` 日志必须在同一事务提交/回滚。put、add、delete、范围删除、clear、cursor.update/delete 都必须追踪；自增键使用请求成功后的真实 key。open/deleteDatabase 的写追踪补丁必须打在 `IDBFactory.prototype` 上而不是 `window.indexedDB` 实例上——WebKit（Safari/iOS）会在其数据库进程被回收后重建 indexedDB 工厂实例，实例级补丁会静默消失而 transaction 原型补丁仍在，新连接无 journal 导致所有业务写入与云上传失败（iOS Safari 实测故障）；restore-sim/scale-sim 沙箱已提供 `IDBFactory` 全局，并把这两个补丁点纳入 PATCHED_MEMBERS 原型快照清理。

3. localStorage 写入前创建独立 `rp_sync_intent_v2:<uuid>` 意图。只有云端提交成功并确认水位后才能删除；上传期间产生的新日志/意图保留到下一轮。

4. 候选键按单连接、每 64 键批量读取。首次全扫事务最多 64 条并受约 8MiB 估算边界约束。

5. canonical JSON 保持键排序并拒绝 undefined、NaN、bigint 和循环引用。以下变化必须为零新 pack、零提交：
   - 同值 put
   - 对象属性顺序变化
   - 同一日志窗口改后改回
   - clear 后原样回填
   - store 定义等价时仅 IndexedDB version 变化

6. `updateCachedSnapshot` 中每一个缓存 entry 写入或删除之前，都必须先持久化 `pendingBuckets`。这是崩溃安全不变量，`audit-regressions` 有结构断言。

7. 索引缺失、缓存版本变化、追踪 epoch 重置时，只能经确认完整重建本地索引。重建只读本地。

8. 上传/下载为整体替换语义（单用户产品决策，最后一次完整上传生效）：上传用本机数据整体替换云端（本机为空则清空云端）；下载用云端整体替换本机。客户端不做跨设备基线比对与自动合并；服务器端只保留根 ETag 条件写和校验，CAS 竞争由 Worker 自动重读并收敛，不因设备或维护请求让用户重试。

9. 不同步：`rp_hub_presets`、同步密码、自动保存开关与分钟配置、上次同步徽标（`rp_hub_sync_last_result_v1`，bootstrap.js 启动时读入同步浮窗头部右侧，格式 `16:30 同步成功/同步失败`）、RPHubSyncCache、RPHubSyncStaging、日志 store、意图键、epoch、恢复状态键。

10. 自动保存只使用一个前台 one-shot 定时器，不使用高频轮询：打开或刷新页面重新计时；隐藏、pagehide、freeze 时暂停，pageshow、resume 或重新可见时继续；电脑休眠没有跨浏览器可靠事件，延迟回调按保守策略不立即补传。自动保存复用现有上传 runner、当前页 `state.syncing/operationPending` 防重复操作和服务端幂等会话，无变化也执行 checksum 检查，失败等待下一完整周期，不自动弹窗或自动重建失效索引。

四、免费版资源边界

1. 设计预算：Workers Free 每请求 10ms CPU、6 个同时出站连接、128MiB isolate；项目自定每请求 50 子请求保守预算（官方外部 50、内部 R2/KV 1000 应区分）；请求/日和 R2 月额度以 Cloudflare 当前官方规则为准。

2. 代码硬上限：快照 1GiB、8192 pack、单 pack 1MiB/512 条、manifest page 32 pack、Bloom 32KiB、GC page 256。

3. 禁止以下回归：
   - 一个请求上传多个 pack；
   - Worker 聚合或复制大正文；
   - finalize 扫描完整 manifest 或完整 pack 目录；
   - 在一个请求中无界 Promise.all；
   - GC 放在 finalize 或 waitUntil；
   - 下载相信未绑定 manifest 位置的 checksum。

4. 本地 `sync-v13-budget` 使用小堆、R2 流外部托管，硬门槛 p95 ≤10ms、max ≤20ms、子请求 ≤50、R2 并发 ≤6；并发压力阶段（8 路同 isolate upload-pack、4 推 + 4 拉混合）逐请求套用同一门槛——客户端上传并发不得改变单请求预算结论。
   它是高分辨率墙钟代理，不是 Cloudflare 官方 CPU。部署后仍要看 Metrics 和 1102 错误。

5. 2026-10-13 300MB 验证结果（256 桶/32 项数组布局）：
   - 首次：0.293GiB、530 pack、448 字节 root、575 请求；
   - 无变化：1 请求、0 pack；
   - 100 条等长修改：90 新 pack、79.7MiB、134 请求、业务全扫游标 0；
   - 20 加长 + 10 删除 + 10 新增：52 新 pack、27.6MiB、93 请求、业务全扫游标 0；
   - 最终恢复：38,820 条、530 pack、547 个拉取请求、最大并发 4、133 个 staging 读取事务；
   - 恢复每条记录固定解析 2 次、每个 staging pack 固定读取 1 次、缓存命中不重哈希；
   - 峰值：35 子请求、客户端并发 4、R2 put 1MiB；R2 Class B 随宿主 gc-step 批次数小幅波动。
   - 宿主墙钟不等同 Cloudflare CPU。

6. 最新独立预算见 DEVELOPMENT.md 第 5 节：upload-pack 3 子请求（isolate 页缓存命中后），manifest page 34/并发 6（isolate 内已验包免 head），finalize 5，pull page 1，pull pack 2，GC 8；本地墙钟不是 Cloudflare CPU。

五、图片与图库不变量

1. 图片 key、作者角色/聊天存储格式和固定记录路径保持兼容。固定记录继续保存在 `RPHubDB/store/rp_hub_image_renders_<角色UUID>`，并按 storyScopeId 隔离。

2. 网络任务按读取 URL 共享；每个角色/消息/槽位独立提交记录。旧失败不能删除新任务的记录；成功记录继续复用；任务 Map 结束后清理，已结算槽位受上限淘汰。

3. 图库管理页整库单次加载：`/image/api/library` 循环翻页列出全部对象后一次性返回所有角色分组，前端一次 load 渲染全部角色卡，不做“加载下一批”；每张角色卡默认只渲染 8 张缩略图（≤720px 视口 6 张），卡内“显示更多”按钮纯前端按页追加，不产生额外请求。后端 library 的墓碑过滤用一次墓碑前缀全列集合比对（`listImageTombstoneKeys`），不逐对象 head。删除保持两阶段：先写墓碑并返回，再后台批量删除原图/缩略图。每请求最多 20 个目标，清空分组通过服务端 continuation 游标续传（游标分页的 `listImageObjects` 变体仅供 delete 目录展开使用）；失败 tombstone 必须保留在响应中供重试。

4. 墓碑不能当工作区垃圾或 R2 垃圾删除。主 `/api/rp-image` 读取按墓碑优先（先查墓碑再查原图），删除后的生图读取立即返回占位图；后台物理删除失败时残留原图不会泄漏，会在下次打开图库时被后台清理。图库管理端点的墓碑优先策略尚未统一，不能扩大为全端点权限或读取保护承诺。

5. 图片/缩略图继续执行 64MiB/2MiB 流式上限和正文停滞超时。作者回源必须剥离 Cookie、Authorization 和 `x-rp-sync-password`。

6. 生图门控使用作者自己的“自动生图”世界书开关（`worldInfo` 中 `comment === '自动生图'` 条目的 `enabled`，即 `isAutoImageGenEnabled`），经外部适配脚本读取 Vue 内存状态，在每次任务创建时实时传入 `autoImageGen`。开关关闭时不发起任何生成请求；无记录槽位的卡片以 `.magic-image-suppressed{display:none!important}` 整体隐藏（无图、无加载占位、无错误卡），隐藏任务的 promise 正常完成供作者 reroll 流程等待。有记录的旧消息照常显示旧图；关闭时重掷已显示旧图的槽位保留旧图不再生成。不做槽位压制持久化：重新打开开关后，之前因关闭而隐藏且无记录的槽位按作者原生行为重新生成。

7. 适配层传入 autoImageGen 时先确认世界书已加载且状态字段存在，否则传 undefined，图片业务按原生生成语义放行。角色/分支/消息上下文缺失则不接管。“固定生图”开关保持纯持久化语义（只决定生成结果是否落盘为固定记录），不参与生成门控；其设置行样式仍来自适配层 ui.settings。

8. 生图提供商由密钥决定：`imageGenKey` 以 `YNAI-` 开头（不分大小写）时 provider 为 `ynai`，Worker 转发到中转站的 OpenAI images 形状（POST `/v1/images/generations`、`b64_json` 应答、尺寸映射 竖图 832x1216 / 横图 1216x832 / 方图 1024x1024）；其余一律 `sta1n` 原生生成。生成只走 POST（含固定记录重放与 reroll），GET 仅读取缓存，无缓存时 404。YNAI JSON 响应受有界读取保护，解码图片上限 16MiB；固定生图开关只决定结果是否落盘，不得绕过本项目 URL 规范化、YNAI 路由或已有记录读取。空 steps 默认按提供商区分：ynai 28、sta1n 40；未显式带 `model` 的 ynai 请求默认值取云端 `image.ynai.defaultModel`（配置缺失回退内置 `nai-diffusion-4-5-full`，sta1n 恒用内置默认），默认值在签名计算前解析，缓存键与实际模型一致。**中转端点只认云端适配脚本头部元数据 `image.ynai` 段（base/modelsPath/generatePath/defaultModel），无代码兜底**——配置缺失或形状非法时模型端点与 ynai 生成显式报 503；**缓存不区分来源**：`provider` 不再是 URL 参数键，签名的 provider 字段恒为 `'sta1n'`，两个提供商共享同一内容寻址缓存，历史键稳定，URL/快照不携带 provider。`GET /api/rp-image-models` 以 `x-rp-image-token` 头转发中转站 `/v1/models`（仅接受 YNAI- 密钥，30 秒内存缓存，写入前淘汰过期条目）；魔改层劫持作者设置页“生图版本”浮窗（按 ui.settings.modelLabel 定位，隐藏 custom-select 并原位放入同款 select），选项来自该端点（列表镜像存 `rp_hub_magic_ynai_models`），默认模型取 `image.ynai.defaultModel`（无则取列表第一个），选择存 `rp_hub_magic_ynai_model` 并在构建请求时覆盖 `model` 参数；固定记录重放使用生成时快照的模型。不使用作者页面的 provider UI（作者已移除多中转），不为此改写作者源码。
